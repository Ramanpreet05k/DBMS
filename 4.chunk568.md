## 1. Database Anomalies (The Bugs of Bad Design)

Anomalies happen when you try to cram too much unrelated data into a single table.

| EmpID | EmpName | Role | DeptID | DeptName    | DeptHead |
| :---- | :------ | :--- | :----- | :---------- | :------- |
| 101   | Alice   | Dev  | D1     | Engineering | Charlie  |
| 102   | Bob     | QA   | D1     | Engineering | Charlie  |

*   **Insertion Anomaly:** When certain data cannot be inserted into the database without the presence of other data. You cannot add a new Department (like "Sales") unless you hire an employee for it first, because `EmpID` is the Primary Key and cannot be `NULL`.
*   **Deletion Anomaly:** It refers to the situation where the deletion of data results in the unintended loss of some other important data. If Alice and Bob both quit, you delete their rows. But in doing so, you accidentally delete the fact that "D1 is Engineering and run by Charlie."
*   **Updation Anomaly:** It happens when an update of a single data value requires multiple rows of data to be updated. If Charlie steps down and Diana becomes the new DeptHead, you have to update it in 5,000 different employee rows. Miss one, and your database is corrupted.

## 2. Functional Dependencies (FDs)

A Functional Dependency is just a rule describing how columns relate. Written as $X \rightarrow Y$ (X determines Y).

*   **Non-Trivial FD (The Useful One):** $X \rightarrow Y$. If I know X, I can find Y. (Example: `EmpID` $\rightarrow$ `EmpName`).
*   **Trivial FD (The Obvious One):** $X \rightarrow Y$ where Y is just a part of X. (Example: `{EmpID, EmpName} \rightarrow EmpID`). ($X \cap Y = \emptyset$)
*   **Transitive FD (The 3NF Violator):** A determines B, and B determines C. Therefore A determines C. (Example: `EmpID` $\rightarrow$ `DeptID`, and `DeptID` $\rightarrow$ `DeptName`. Therefore `EmpID` determines `DeptName`).
*   **Multi-valued Dependency (The 4NF Violator):** When one key determines multiple independent values. (Example: An employee has multiple Skills and multiple Hobbies, but skills and hobbies don't affect each other).

## 3. Closures & Minimal Cover

**Attribute Closure ($X^+$):**
If I hand you one specific column (like `EmpID`), and you use all the rules given to you, what is the absolute maximum number of columns you can figure out? If you give me column X, what is the complete list of every other column I can figure out using the FD rules?

> **FAANG Interview Trick:** If the closure of a column includes every column in the table, you have just found your Super Key!

**Minimal / Canonical Cover:**
The absolute smallest, mathematically stripped-down set of FD rules needed to describe your database without repeating yourself.

## 4. Normalization Overview
*   A step towards DB Optimization.
*   Used to minimize redundancy from relations.
*   Used to eliminate undesirable characteristics like insertion, deletion, and updation anomalies.
*   Normal forms are used to reduce redundancy from the DB.

## 5. Normal Forms

Normalization is a step-by-step process of breaking down one massive, messy table into smaller, logically organized tables to eliminate data duplication and prevent bugs (called **anomalies**) when updating, inserting, or deleting data.

Let's imagine a startup that tracks all its sales in one giant, messy spreadsheet.

### Unnormalized Form (UNF): The Messy Spreadsheet
In UNF, there are no rules. Data is often grouped together in arrays or lists.

**Table: `Sales_Data`**

| OrderID | CustomerID | CustomerName | ZipCode | City | Items_Purchased (ID, Name, Price, Qty) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 101 | C1 | Alice | 10001 | New York | `[I-1, Laptop, $1000, 1]`, `[I-2, Mouse, $50, 2]` |
| 102 | C2 | Bob | 90210 | Beverly Hills | `[I-1, Laptop, $1000, 1]` |
| 103 | C1 | Alice | 10001 | New York | `[I-3, Keyboard, $80, 1]` |

**The Problem:** You cannot easily query this database to find out how many total "Mice" were sold, because that data is trapped inside a comma-separated list.

### First Normal Form (1NF): "Keep It Atomic"
**The Rule:** Every cell must hold a single, indivisible (atomic) value. No arrays or lists.

To fix our table, we must flatten the data by creating a new row for every single item purchased.

**Table: `Sales_1NF`**

| OrderID | CustomerID | CustomerName | ZipCode | City | ItemID | ItemName | Price | Qty |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 101 | C1 | Alice | 10001 | New York | I-1 | Laptop | $1000 | 1 |
| 101 | C1 | Alice | 10001 | New York | I-2 | Mouse | $50 | 2 |
| 102 | C2 | Bob | 90210 | Beverly Hills | I-1 | Laptop | $1000 | 1 |
| 103 | C1 | Alice | 10001 | New York | I-3 | Keyboard | $80 | 1 |

*Note: The Primary Key for this table is now a **Composite Key**: `{OrderID, ItemID}`. You need both to uniquely identify a row.*

**The Problem:** We have massive redundancy. If the price of a Laptop changes to $1200, we have to update it in multiple rows. If Alice changes her name, we have to update it in three places.

### Second Normal Form (2NF): "The Whole Key"
**The Rule:** It must be in 1NF, and there can be no **Partial Dependencies**. Every non-key column must depend on the *entire* Primary Key, not just a part of it.

Looking at our 1NF table, the Primary Key is `{OrderID, ItemID}`.
*   `Qty` depends on both (how many of *this item* were in *this order*).
*   `CustomerName` only depends on `OrderID`. (Partial dependency!)
*   `ItemName` only depends on `ItemID`. (Partial dependency!)

To reach 2NF, we break the data into three separate tables:

**Table 1: `Orders`** (Depends only on OrderID)

| OrderID | CustomerID | CustomerName | ZipCode | City |
| :--- | :--- | :--- | :--- | :--- |
| 101 | C1 | Alice | 10001 | New York |
| 102 | C2 | Bob | 90210 | Beverly Hills |
| 103 | C1 | Alice | 10001 | New York |

**Table 2: `Items`** (Depends only on ItemID)

| ItemID | ItemName | Price |
| :--- | :--- | :--- |
| I-1 | Laptop | $1000 |
| I-2 | Mouse | $50 |
| I-3 | Keyboard | $80 |

**Table 3: `Order_Details`** (Depends on the whole composite key)

| OrderID | ItemID | Qty |
| :--- | :--- | :--- |
| 101 | I-1 | 1 |
| 101 | I-2 | 2 |
| 102 | I-1 | 1 |
| 103 | I-3 | 1 |

### Third Normal Form (3NF): "Nothing But The Key"
**The Rule:** It must be in 2NF, and there can be no **Transitive Dependencies**. A non-key column cannot depend on another non-key column.

Look closely at our 2NF `Orders` table. The Primary Key is `OrderID`.
*   Does `City` depend on the `OrderID`? No. `City` depends on the `ZipCode`.
*   Does `CustomerName` depend on the `OrderID`? No. It depends on the `CustomerID`.

**Table 1: `Orders_3NF`**

| OrderID | CustomerID |
| :--- | :--- |
| 101 | C1 |
| 102 | C2 |
| 103 | C1 |

**Table 2: `Customers`**

| CustomerID | CustomerName | ZipCode |
| :--- | :--- | :--- |
| C1 | Alice | 10001 |
| C2 | Bob | 90210 |

**Table 3: `Locations`**

| ZipCode | City |
| :--- | :--- |
| 10001 | New York |
| 90210 | Beverly Hills |

*(The `Items` and `Order_Details` tables remain exactly the same as they were in 2NF).*

**Result:** The database is now highly robust. If a city changes its name, you update exactly *one* cell in the `Locations` table, and every order updates automatically.

### Boyce-Codd Normal Form (BCNF): "The Stricter 3NF"
3NF is usually where software engineers stop. However, BCNF handles a rare edge case where a table has overlapping candidate keys.

**The Rule:** For every dependency $X \rightarrow Y$, X must be a Super Key.

**The BCNF Edge Case Table: `College_Advising`**
Imagine a rule: A student can major in many subjects. Every subject has multiple advisors, but an advisor only teaches *one* subject.

| StudentID | Subject | Advisor |
| :--- | :--- | :--- |
| S1 | CompSci | Prof. Smith |
| S1 | Math | Prof. Jones |
| S2 | CompSci | Prof. Davis |

*   **The Primary Key:** `{StudentID, Subject}` (S1 and CompSci determines the advisor is Smith).
*   **The Violation:** Look at the rule: `Advisor` determines the `Subject`. (If I know it is Prof. Davis, I know the subject is CompSci). However, `Advisor` is **not** a Primary/Super Key for this table.

**The BCNF Fix:** Break it out.
1.  **`Student_Advisors` Table:** `[StudentID, Advisor]`
2.  **`Advisor_Subjects` Table:** `[Advisor, Subject]`

## 6. Denormalization

**Denormalization** is the strategic, intentional process of combining separate tables back together, deliberately introducing data redundancy (duplication) into your database.

### 1. Why do we Denormalize? (The FAANG Use Case)
In a perfectly normalized database, data is incredibly safe to *write*, but it can be extremely slow to *read*. If you are building a system heavily skewed toward **Reads** (e.g., 1000 reads for every 1 write), a database forced to perform multiple `JOIN` operations will crash under the CPU load.

**We denormalize to eliminate `JOIN` operations and achieve lightning-fast read speeds.**

### 2. The Dummy Data Example
#### The Normalized Way (3NF - Safe but Slow)
**Table 1: `Users`**

| UserID | Name | AvatarURL |
| :--- | :--- | :--- |
| U1 | Alice | /img/alice.jpg |

**Table 2: `Posts`**

| PostID | UserID | Content |
| :--- | :--- | :--- |
| P1 | U1 | "Hello World!" |
| P2 | U1 | "Learning Databases" |

*   *Read Speed:* **Slow.** Requires CPU-heavy `JOIN` logic.
*   *Write Speed:* **Fast.** Easy to update user data.

#### The Denormalized Way (Fast but Risky)
**Table: `Denormalized_Posts`**

| PostID | UserID | Name | AvatarURL | Content |
| :--- | :--- | :--- | :--- | :--- |
| P1 | U1 | Alice | /img/alice.jpg | "Hello World!" |
| P2 | U1 | Alice | /img/alice.jpg | "Learning Databases" |

*   *Read Speed:* **Instant.** No `JOIN` required.
*   *Write Speed:* **Slow & Risky.** Introduces the **Updation Anomaly**.

### 3. How to Handle the Trade-offs
*"If you denormalize, how do you deal with the updation anomalies?"*

**Answer:** **"We handle it in the application layer."**
Use background workers via message queues (Kafka, RabbitMQ, SQS) to asynchronously update duplicated data without slowing down the main application.

### 4. Rule of Thumb for System Design
*   **Use Normalization (3NF) for: OLTP** (Online Transaction Processing). Write-heavy systems like Banking ledgers and E-commerce checkouts.
*   **Use Denormalization for: OLAP** (Online Analytical Processing) and **Read-Heavy Systems**. Social media feeds, Data Warehouses, and massive analytics dashboards.

> **NOTE:** For 2NF: Check each column depend upon ENTIRE PK. For 3NF: Check Non Key on Non Key Dependency.

# Chunk 6: Internal Storage & File Organization

## 1. Storage Hierarchy (The Cost vs. Speed Trade-off)
Databases move data up and down this hierarchy to balance speed and cost.

*   **Primary Storage (Cache, RAM):** Volatile, extremely fast, very expensive. (Use Case: Query execution buffers, Redis).
*   **Secondary Storage (SSD, HDD):** Non-volatile, slower, cheaper. (Use Case: Actual database files).
*   **Tertiary Storage (Magnetic Tapes, Optical):** Non-volatile, incredibly slow, extremely cheap. (Use Case: Cold backups, AWS Glacier).

## 2. Record Organization (How rows are packed)
*   **Fixed-Length Records:** Every row takes up the exact same amount of space.
    *   *Pro:* Super fast reads.
    *   *Con:* Wastes space.
*   **Variable-Length Records:** Rows vary in size (`VARCHAR`).
    *   *Pro:* Saves storage space.
    *   *Con:* Requires overhead formatting.

## 3. File Organization (How rows are arranged on the disk)
*   **Heap Organization:** Dump the new row wherever there is free space.
    *   *Pro:* Fast `INSERT`.
    *   *Con:* Horrible searching (Full Table Scans).
*   **Sequential Organization:** Records sorted physically on disk.
    *   *Pro:* Excellent for range queries.
    *   *Con:* `INSERT` is slow.
*   **Hash Organization:** Math hash function applied to the key.
    *   *Pro:* Instant $O(1)$ lookups for exact matches.
    *   *Con:* Useless for range queries.
*   **Clustered File Organization:** Intentionally interleaves rows from joined tables on the exact same physical disk block to eliminate expensive disk I/O.

## 4. RAID (Protecting the Data)

| RAID Level | Strategy | How it Works | Context |
| :--- | :--- | :--- | :--- |
| **RAID 0** | **Striping** | Splits a file in half and writes each half to two different disks simultaneously. | **Danger!** Double the speed, but zero safety. Never use for databases. |
| **RAID 1** | **Mirroring** | Writes the exact same data to two disks. | **Safe but Expensive.** Cuts your total storage capacity in half. |
| **RAID 5** | **Parity** | Stripes data across at least 3 disks, but reserves some space for mathematical "parity" data. | Can survive 1 disk failure. Slower write speeds. |
| **RAID 10** | **Striping + Mirroring** | A nested array (Combines RAID 1 + RAID 0). | **The Industry Standard.** Blazing speed and safety. |

# Chunk 8: Query Processing & Optimization

## 1. The Processing Pipeline
1.  **Parsing & Translation:** Syntax and semantic checks. Translates SQL into Relational Algebra.
2.  **Optimization:** Generates Execution Plans and picks the absolute cheapest one.
3.  **Evaluation:** Engine runs the plan, fetches data, and returns it.

## 2. Cost Metrics
*   **Disk Access (I/O Cost):** The ultimate bottleneck. The primary goal of the optimizer is to minimize disk blocks read.
*   **CPU Time:** Cost of sorting, calculations, and string comparisons.

## 3. Evaluation Techniques
*   **Materialization:** Saves intermediate results to a temporary table on the physical disk. Safe but slow.
*   **Pipelining:** Passes rows directly between steps in RAM. Fast but requires high memory.

## 4. Query Planners
*   **Heuristic Optimization:** Uses hardcoded logical rules (e.g., filter before joining).
*   **Cost-Based Optimization (CBO):** Uses internal table statistics to calculate exact CPU/IO costs to pick the lowest number.

## 5. Execution Plans (`EXPLAIN`)
The ultimate debugging tool. Prepend `EXPLAIN` (or `EXPLAIN ANALYZE`) to see the step-by-step Execution Plan.

| Node Type | What it means | Diagnosis |
| :--- | :--- | :--- |
| **Sequential Scan** | Read every single row top to bottom. | 🚩 **RED FLAG.** Usually missing an Index on the `WHERE` clause. |
| **Index Scan / Seek** | Used a B+ Tree index to jump directly to the disk block. | 🟢 **GREEN FLAG.** Highly efficient $O(\log N)$ disk lookups. |
| **Nested Loop Join** | Loops through Table B for every row in Table A. | ⚠️ **WARNING.** Disastrous for large tables ($O(N \times M)$ complexity). |
| **Hash Join** | Builds an in-memory hash table of the smaller table. | 🟢 **GREEN FLAG.** Excellent for large datasets if RAM permits. |
