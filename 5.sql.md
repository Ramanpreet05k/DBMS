    * Common Table Expressions (CTEs) and Recursive CTEs.

* **Database Objects:**
    * Views (Simple vs. Complex).

    * Triggers (Row-level vs. Statement-level).
    * Stored Procedures, User-Defined Functions (UDFs), and Cursors.

## Chunk 1: The Absolute Basics (Retrieval & Filtering)

### 1. SELECT and FROM (Choosing your data)

```sql
SELECT * FROM employees;

SELECT first_name, last_name, job_title 
FROM employees;
```

### 2. WHERE (Filtering the rows)

```sql
SELECT first_name, last_name 
FROM employees 
WHERE department = 'Sales';
```

**Multiple Conditions (AND, OR):**
```sql
SELECT * FROM employees 
WHERE department = 'Sales' AND salary > 60000;
```

### 3. Advanced Filtering (IN, BETWEEN, LIKE)

```sql
SELECT * FROM employees 
WHERE department IN ('Sales', 'Marketing', 'IT');

SELECT * FROM employees 
WHERE salary BETWEEN 50000 AND 80000;
```

**LIKE:** Used for pattern matching. `%` represents zero, one, or multiple characters. `_` represents a single character.
```sql
SELECT * FROM employees 
WHERE last_name LIKE 'S%';
```

### 4. Sorting and Paging (ORDER BY, LIMIT)

```sql
SELECT first_name, last_name, salary 
FROM employees 
ORDER BY salary DESC;

-- Finds the top 5 highest-paid employees
SELECT first_name, last_name, salary 
FROM employees 
ORDER BY salary DESC 
LIMIT 5;
```

## Chunk 2: Modifying Data & Structure (DDL & DML)

### 1. DDL: Creating and Changing Tables

**CREATE TABLE:** Sets up the table, its columns, data types, and rules (constraints).
```sql
CREATE TABLE employees (
    emp_id INT PRIMARY KEY,           -- Unique identifier for each row
    first_name VARCHAR(50) NOT NULL,  -- Cannot be left blank
    last_name VARCHAR(50) NOT NULL,
    department VARCHAR(50),
    salary DECIMAL(10, 2),            -- Number with 2 decimal places
    hire_date DATE
);
```

**ALTER TABLE:** Modifies an existing table structure (e.g., adding a new column).
```sql
ALTER TABLE employees 
ADD email VARCHAR(100);
```

**DROP TABLE:** Permanently deletes the table and all its data. *Use with extreme caution.*
```sql
DROP TABLE employees;
```

### 2. DML: Inserting, Updating, and Deleting Data

**INSERT INTO:** Adds new rows to a table. You must match the order of the columns you specify.
```sql
INSERT INTO employees (emp_id, first_name, last_name, department, salary, hire_date)
VALUES (1, 'Jane', 'Doe', 'IT', 75000.00, '2023-01-15');
```

**UPDATE:** Modifies existing data. *Crucial: Always use a WHERE clause, or you will accidentally update every single row in the table.*
```sql
-- Gives a raise to a specific employee
UPDATE employees 
SET salary = 80000.00 
WHERE emp_id = 1;
```

**DELETE:** Removes rows from a table. Like UPDATE, if you forget the `WHERE` clause, you will delete everything.
```sql
-- Removes a specific employee
DELETE FROM employees 
WHERE emp_id = 1;
```

## Chunk 3: Aggregation & Grouping

### 1. Aggregate Functions (The Math)

**COUNT():** Finds the total number of rows.
```sql
-- How many employees do we have in total?
SELECT COUNT(*) 
FROM employees;
```

**SUM() and AVG():** Calculates the total or average of a numeric column.
```sql
-- What is our total payroll, and what is the average salary?
SELECT SUM(salary) AS total_payroll, 
       AVG(salary) AS average_salary 
FROM employees;
```

**MIN() and MAX():** Finds the lowest or highest value.
```sql
-- Who was hired most recently? (Max date is the most recent)
SELECT MAX(hire_date) AS newest_hire 
FROM employees;
```

### 2. GROUP BY (Categorizing the Math)

**Grouping by one column:**
```sql
-- How many employees are in each department?
SELECT department, COUNT(*) AS employee_count
FROM employees
GROUP BY department;
```

**Grouping by multiple columns:**
```sql
-- What is the average salary per department, broken down by job title?
SELECT department, job_title, AVG(salary) AS avg_salary
FROM employees
GROUP BY department, job_title;
```

### 3. HAVING (Filtering Aggregated Data)
You cannot use a `WHERE` clause to filter the results of an aggregate function (like COUNT or SUM) because `WHERE` filters rows *before* the math happens. To filter data *after* the math happens, you use `HAVING`.

```sql
-- Show me only the departments where the average salary is greater than $70,000
SELECT department, AVG(salary) AS avg_salary
FROM employees
GROUP BY department
HAVING AVG(salary) > 70000;
```

## Chunk 4: Connecting Data (Joins & Set Operations)

Relational databases split data across multiple tables to avoid duplication. Joins are how you stitch that data back together.

**Imagine we have:**
* `employees` table: `emp_id`, `first_name`, `dept_id`
* `departments` table: `dept_id`, `dept_name`, `location`

### 1. Joins (Combining Columns)
Joins combine columns from two tables based on a related column between them (in this case, `dept_id`).

**INNER JOIN:** The most common join. It returns ONLY the rows where there is a match in both tables.
```sql
-- Get a list of employees and the name of the department they work in
SELECT employees.first_name, departments.dept_name
FROM employees
INNER JOIN departments ON employees.dept_id = departments.dept_id;
```

**LEFT JOIN:** Returns ALL rows from the "left" table (the one after `FROM`), and the matched rows from the "right" table. If an employee hasn't been assigned a department yet, they still show up, but their department info will be `NULL`.
```sql
-- Show ALL employees, even if they don't have a department assigned yet
SELECT employees.first_name, departments.dept_name
FROM employees
LEFT JOIN departments ON employees.dept_id = departments.dept_id;
```

* **RIGHT JOIN:** The exact opposite of a Left Join. It returns ALL departments, even if no employees work there yet.
* **FULL OUTER JOIN:** Returns all records when there is a match in either the left or right table. (Show everyone, and show all departments, matching them where possible).

### 2. Set Operations (Combining Rows)

**UNION:** Combines the results of two queries and removes any exact duplicates.
```sql
-- Imagine we have a separate table for past_employees. 
-- This gets a unique list of all emails, past and present.
SELECT email FROM employees
UNION
SELECT email FROM past_employees;
```

**UNION ALL:** Does the exact same thing as `UNION`, but it keeps duplicates. It is also faster for the database to run because it doesn't have to search for and remove duplicates.
```sql
-- Combines both lists entirely, keeping duplicates if someone is in both
SELECT email FROM employees
UNION ALL
SELECT email FROM past_employees;
```

**INTERSECT (The Overlap):**
`INTERSECT` compares two queries and returns only the rows that appear in both results. It is the middle section of a Venn diagram.
```sql
-- Finds employee IDs that exist in both tables
SELECT employee_id 
FROM project_alpha_team
INTERSECT
SELECT employee_id 
FROM project_beta_team;
```

**EXCEPT / MINUS (The Subtraction):**
This operator returns the rows from the first query that do not appear in the second query. It takes your first list and subtracts anything found in the second list.
```sql
-- Finds everyone on Alpha, and subtracts anyone who is also on Beta
SELECT employee_id 
FROM project_alpha_team
EXCEPT
SELECT employee_id 
FROM project_beta_team;
```

## Chunk 5: Advanced Filtering & Subqueries

### 1. Basic Subqueries
**Scenario:** You want to find all employees who earn more than the company's average salary. (You can't just put `AVG(salary)` in the `WHERE` clause, so you use a subquery).
```sql
SELECT first_name, last_name, salary
FROM employees
WHERE salary > (
    SELECT AVG(salary) 
    FROM employees
);
```

### 2. Correlated Subqueries
**Scenario:** You want to find employees who earn more than the average salary of their specific department (not the whole company).
```sql
SELECT e1.first_name, e1.last_name, e1.salary, e1.department
FROM employees e1
WHERE e1.salary > (
    SELECT AVG(e2.salary)
    FROM employees e2
    WHERE e1.department = e2.department
);
```

### 3. EXISTS vs. IN
When checking if a value matches a list generated by a subquery, you can use `IN` or `EXISTS`. `EXISTS` is often much faster on large datasets because it stops searching the moment it finds a single match (it evaluates to True/False).

**Scenario:** Find all departments that have at least one employee earning over $100,000.
```sql
SELECT department_name 
FROM departments d
WHERE EXISTS (
    SELECT 1 
    FROM employees e 
    WHERE e.dept_id = d.dept_id 
    AND e.salary > 100000
);
```

## Chunk 6: Built-in Functions & Conditionals

### 1. String Functions (Text Manipulation)

**CONCAT():** Joins two or more strings together.
```sql
-- Creates a single "Full Name" column
SELECT CONCAT(first_name, ' ', last_name) AS full_name 
FROM employees;
```

**TRIM():** Removes leading and trailing spaces from a string (often caused by accidental keystrokes during data entry). You can also use `LTRIM()` for left spaces and `RTRIM()` for right spaces.
```sql
SELECT TRIM(email) AS clean_email 
FROM employees;
```

**UPPER() and LOWER():** Converts text to all uppercase or all lowercase. This is incredibly useful in `WHERE` clauses to make your searches case-insensitive.
```sql
SELECT first_name 
FROM employees 
WHERE LOWER(department) = 'sales';
```

**SUBSTRING():** Extracts a specific portion of a string. You provide the string, the starting position, and the number of characters to extract.
```sql
-- Extracts the first 3 characters of a phone number (the area code)
SELECT SUBSTRING(phone_number, 1, 3) AS area_code 
FROM employees;
```

**REPLACE():** Finds a specific string of characters and replaces it with another.
```sql
-- Replaces 'Jr.' with 'Junior' in job titles
SELECT REPLACE(job_title, 'Jr.', 'Junior') AS updated_title 
FROM employees;
```

### 2. Date & Time Functions (Temporal Data)

**Current Date/Time:** Grabbing the exact moment the query is run.
```sql
SELECT CURRENT_DATE AS today, 
       CURRENT_TIMESTAMP AS right_now;
```

**EXTRACT() / DATEPART():** Pulls a specific component (year, month, day) out of a date.
```sql
-- Finds everyone hired in the year 2023
SELECT first_name, hire_date 
FROM employees 
WHERE EXTRACT(YEAR FROM hire_date) = 2023;
```

**Date Math (DATEDIFF / INTERVAL):** Adding or subtracting time.
```sql
-- Calculates how many days an employee has been with the company (PostgreSQL syntax)
SELECT first_name, 
       CURRENT_DATE - hire_date AS days_employed 
FROM employees;
```

### 3. Math & Casting Functions

**Rounding Numbers:**
* **ROUND(column, decimal_places):** Rounds to the nearest specified decimal.
* **CEIL(column):** Always rounds up to the nearest whole number.
* **FLOOR(column):** Always rounds down to the nearest whole number.
```sql
SELECT salary, 
       ROUND(salary / 12, 2) AS monthly_salary 
FROM employees;
```

**CAST():** Converts data from one type to another. For example, if a price was accidentally stored as text (`VARCHAR`), you must cast it to a number before you can sum it.
```sql
-- Standard SQL syntax
SELECT CAST(salary_as_text AS DECIMAL(10,2)) 
FROM employees;
```

### 4. Conditional Logic (SQL's IF/THEN)

**CASE WHEN:**
```sql
-- Categorizing employees based on their tenure
SELECT 
    first_name,
    hire_date,
    CASE 
        WHEN EXTRACT(YEAR FROM hire_date) < 2015 THEN 'Veteran'
        WHEN EXTRACT(YEAR FROM hire_date) BETWEEN 2015 AND 2021 THEN 'Experienced'
        ELSE 'New Hire'
    END AS employee_status
FROM employees;
```

**COALESCE():** A lifesaver for missing data (`NULL` values). It accepts a list of values and returns the first one that is not null.
```sql
-- If cell_phone is NULL, check home_phone. If that is NULL, print 'No Contact'.
SELECT 
    first_name, 
    COALESCE(cell_phone, home_phone, 'No Contact') AS best_phone_number
FROM employees;
```

**NULLIF():** Compares two values. If they are equal, it returns `NULL`. If they are different, it returns the first value. *Pro-tip: This is most commonly used to prevent "Divide by Zero" errors.*
```sql
-- If total_sales is 0, NULLIF turns it into NULL. 
-- Dividing by NULL returns NULL instead of crashing your entire query.
SELECT 
    department,
    total_revenue / NULLIF(total_sales, 0) AS average_revenue_per_sale
FROM department_stats;
```

## Chunk 7: Window Functions (Advanced Analytics)

Every window function requires the `OVER()` clause. This tells SQL, "Hey, don't just look at this one row; look at a 'window' of rows related to this one."

Inside `OVER()`, you typically use two commands:
* **PARTITION BY:** This is the window function version of `GROUP BY`. It divides the data into groups (e.g., by department).
* **ORDER BY:** This determines the order of the rows inside that specific window.

### 1. Ranking Functions
These assign a rank or row number to each record based on a specific order.

**Scenario:** We want to rank employees by their salary within their specific department.
```sql
SELECT 
    first_name, 
    department, 
    salary,
    -- Simple row number (1, 2, 3...)
    ROW_NUMBER() OVER(PARTITION BY department ORDER BY salary DESC) AS row_num,
    
    -- Rank (If there's a tie for 1st, the next person is 3rd: 1, 1, 3)
    RANK() OVER(PARTITION BY department ORDER BY salary DESC) AS rank_num,
    
    -- Dense Rank (If there's a tie for 1st, the next person is 2nd: 1, 1, 2)
    DENSE_RANK() OVER(PARTITION BY department ORDER BY salary DESC) AS dense_rank_num
FROM employees;
```

**RANK() vs DENSE_RANK():** Both functions assign a ranking number to rows based on your `ORDER BY` clause. But when two rows have the exact same value, their behavior splits:
* **RANK()** skips numbers after a tie. If two people tie for 2nd place, they both get a 2. The next person in line gets a 4. (There is no 3rd place).
* **DENSE_RANK()** never skips numbers. If two people tie for 2nd place, they both get a 2. The next person in line gets a 3.

```sql
SELECT 
    player_name, 
    score,
    RANK() OVER (ORDER BY score DESC) AS standard_rank,
    DENSE_RANK() OVER (ORDER BY score DESC) AS dense_rank
FROM leaderboard;
```

| player_name | score | standard_rank | dense_rank |
| :--- | :--- | :--- | :--- |
| Alice | 1000 | 1 | 1 |
| Bob | 850 | 2 | 2 |
| Charlie | 850 | 2 | 2 |
| Diana | 700 | 4 (Skipped 3) | 3 (Next consecutive number) |
| Eve | 650 | 5 | 4 |

### 2. Value / Offset Functions (LAG and LEAD)
These functions allow a row to "look" at the data in the row immediately before or after it. This is essential for calculating month-over-month growth or comparing adjacent values.
* **LAG():** Looks back at previous rows.
* **LEAD():** Looks forward to upcoming rows.

**Scenario:** We want to order employees by their hire date and compare each employee's salary to the person hired immediately before them.
```sql
SELECT 
    first_name,
    hire_date,
    salary,
    -- Look at the salary of the row directly preceding this one
    LAG(salary) OVER(ORDER BY hire_date) AS prev_hired_salary,
    
    -- Calculate the difference between current and previous
    salary - LAG(salary) OVER(ORDER BY hire_date) AS salary_difference
FROM employees;
```
*(For the very first employee hired, LAG() will return NULL because there is no one before them).*

### 3. Aggregate Window Functions (Running Totals)

You can use standard aggregate functions (`SUM`, `AVG`, `MIN`, `MAX`) as window functions. By combining `SUM()` with `ORDER BY` inside the `OVER()` clause, you create a running total.

**Scenario 1:** We want to see the cumulative (running) total of our payroll as we hire new employees over time.
```sql
SELECT 
    first_name,
    hire_date,
    salary,
    -- Because we use ORDER BY, it adds the current row's salary to the previous total
    SUM(salary) OVER(ORDER BY hire_date) AS running_payroll_total
FROM employees;
```

**Scenario 2:** We want to compare an employee's salary to the average salary of their department, without losing the employee's individual name and details (which would happen if we used `GROUP BY`).
```sql
SELECT 
    first_name,
    department,
    salary,
    -- Notice there is no ORDER BY here. It just calculates the average for the partition.
    AVG(salary) OVER(PARTITION BY department) AS dept_avg_salary
FROM employees;
```

## Chunk 8: Organization & Architecture (CTEs & Views)

This chunk is all about organizing your SQL so it is modular, readable, and reusable.

### 1. CTEs (Common Table Expressions)
A CTE allows you to create a temporary, named result set that exists only for the duration of your query. It is a much cleaner alternative to writing nested subqueries. You initiate a CTE using the `WITH` clause.

**Scenario:** We want to find all employees who earn more than the average salary of the entire company, but we want the code to be highly readable.
```sql
-- Step 1: Define the CTE
WITH CompanyAverage AS (
    SELECT AVG(salary) AS avg_sal 
    FROM employees
)
-- Step 2: Query against the CTE and the main table
SELECT 
    e.first_name, 
    e.salary
FROM employees e
JOIN CompanyAverage ca ON e.salary > ca.avg_sal;
```

### 2. Recursive CTEs
This is a special type of CTE that references itself. It is specifically used for querying hierarchical data, like a company organization chart (where an employee has a manager, and that manager has a manager).

**Scenario:** We want to trace the management chain starting from the CEO down to the entry-level employees.
```sql
WITH RECURSIVE OrgChart AS (
    -- Base Case: Find the CEO (who has no manager)
    SELECT emp_id, first_name, manager_id, 1 AS hierarchy_level
    FROM employees
    WHERE manager_id IS NULL
    
    UNION ALL
    
    -- Recursive Step: Join the CTE to the employees table to find subordinates
    SELECT e.emp_id, e.first_name, e.manager_id, oc.hierarchy_level + 1
    FROM employees e
    JOIN OrgChart oc ON e.manager_id = oc.emp_id
)
SELECT * FROM OrgChart ORDER BY hierarchy_level;
```

### 3. Views
If you write a massive 50-line query that joins five tables and calculates complex metrics, you don't want to rewrite it every week. A View allows you to save that query in the database as a "virtual table."

```sql
-- Creating the View
CREATE VIEW active_high_earners AS
SELECT first_name, last_name, department, salary
FROM employees
WHERE salary > 100000 AND status = 'Active';

-- Now you can query the View exactly like a normal table!
SELECT * FROM active_high_earners WHERE department = 'IT';
```

### 4. Materialized Views
Unlike standard views, Materialized Views *do* physically store the resulting data. This is used for extremely heavy analytical queries that take minutes to run. Because the data is saved, querying the materialized view is instant. The catch? You have to manually "refresh" it to get new data.

```sql
CREATE MATERIALIZED VIEW monthly_sales_summary AS
SELECT month, SUM(revenue) as total_rev 
FROM massive_sales_table 
GROUP BY month;

-- Later, when new data is added, you update the view:
REFRESH MATERIALIZED VIEW monthly_sales_summary;
```

## Chunk 9: Database Programming & Optimization (Mastery)

### 1. Transactions (Safety & ACID Properties)
A transaction ensures that a group of SQL statements either all succeed or all fail together. This prevents partial data corruption.
* **BEGIN:** Starts the transaction.
* **COMMIT:** Saves the changes permanently.
* **ROLLBACK:** Undoes everything if an error occurs.

**Scenario:** A bank transfer. You must deduct money from Account A and add it to Account B. If the database crashes after deducting the money but before adding it, the money vanishes. Transactions prevent this.
```sql
BEGIN;

UPDATE accounts SET balance = balance - 500 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 500 WHERE account_id = 2;

-- If both updates work perfectly, you run:
COMMIT;

-- If the second query throws an error, you run this to undo the first one:
ROLLBACK;
```

### 2. Indexes (Performance)
An index works exactly like the index at the back of a textbook. Instead of scanning every single row in a table to find a specific employee (a "Full Table Scan"), the database uses the index to jump instantly to the right row.

```sql
-- Creating an index on the last_name column
CREATE INDEX idx_emp_last_name 
ON employees(last_name);
```

### 3. Query Optimization (EXPLAIN)
If a query is running slowly, you can put the word `EXPLAIN` (or `EXPLAIN ANALYZE` in PostgreSQL) in front of it. The database won't just output the data; it will output its Execution Plan, showing you exactly how it intends to search the tables and where the bottlenecks are.

```sql
EXPLAIN ANALYZE 
SELECT * FROM employees WHERE last_name = 'Smith';
```

### 4. Stored Procedures
A stored procedure is a saved, reusable block of SQL code that can accept parameters and execute complex DML operations (Inserts, Updates, Deletes). Think of it as writing a custom function in Python or JavaScript, but directly in the database.

```sql
-- Conceptual Example (Syntax varies heavily by SQL dialect)
CREATE PROCEDURE GiveDepartmentRaise (IN dept_name VARCHAR, IN percent_raise DECIMAL)
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE employees 
    SET salary = salary + (salary * percent_raise)
    WHERE department = dept_name;
END;
$$;

-- To execute it:
CALL GiveDepartmentRaise('Sales', 0.05);
```

### 5. Triggers (Automation)
A trigger is a piece of SQL code that automatically fires when a specific event (`INSERT`, `UPDATE`, or `DELETE`) happens to a table.

**Scenario:** You want to maintain a strict audit log. Every time someone's salary is updated in the `employees` table, you want the database to automatically write a record of the old salary and new salary into an `audit_log` table.

*(Syntax varies heavily by dialect, but the logic is always the same:)*
```sql
CREATE TRIGGER audit_salary_change
AFTER UPDATE ON employees 
FOR EACH ROW
EXECUTE PROCEDURE audit_function();
```
